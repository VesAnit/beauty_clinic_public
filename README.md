## Business problem

Clinics receive a steady stream of repetitive questions: procedure prices and duration, which specialist performs a treatment, available slots, registration, booking changes, cancellations. Human administrators cannot scale to 24/7 instant responses; clients drop off when they wait.

**Astra** is a conversational clinic administrator that:

- answers in natural language, grounded in the clinic’s own procedure and schedule data  
- guides new clients through verification and registration without exposing internal records  
- books and cancels appointments with slot-level consistency on the doctor’s calendar  
- enforces privacy boundaries (account owner only, no third-party lookups)

## Demonstration notebook

`clinic_admin_demo.ipynb` walks through a single demo client:

1. **Database snapshot** — confirms seeded clinic data is reachable  
2. **Onboarding** — name and phone collection (same pre-agent flow as Telegram `/start`)  
3. **Procedure consultation** — one real **LLM agent turn** with natural-language procedure search (text-to-SQL over Postgres, not vector RAG)  
4. **Schedule** — doctor availability for a chosen date  
5. **Registration** — clinic profile creation when the client is not yet in the database  
6. **Booking** — appointment creation with duration-aware slot reservation  
7. **Verification** — list upcoming visits  
8. **Cancellation** — release slots and remove the appointment row  

Sections 4–8 call the **same service layer** the production tools use, so you see JSON and DB effects directly. Section 3 uses the **full dialog agent** so the client-facing reply is generated by the model after a tool-backed lookup.

**Deliberately omitted from the notebook** (still present in production): Telegram transport, Redis job queue, input/output guardrail classifiers, verbose tool traces.

**Requirements to run the notebook:** Python 3.10+, project venv from the **private** repository, Postgres with migrated schema and seed data, local LLM inference (vLLM) for the agent section, `.env` aligned with production configuration.

## Production architecture (private repository)


### Queue and concurrency (Redis)

- **Global stream** with consumer groups for horizontal workers.  
- **Per-user lock** so one client never has two agent turns interleaved.  
- **Held queue** while a turn is in progress — strict FIFO per Telegram user.  
- **Idempotency** on Telegram `update_id` to survive retries and duplicates.  
- **Concurrency cap** on active turns to protect GPU/LLM capacity.

### Worker (background processor)

- Pulls jobs, routes onboarding vs registration vs agent dialog (same rules the notebook mirrors manually).  
- Invokes the dialog agent, sends replies back to Telegram, triggers follow-up system prompts (e.g. birth date / email after registration start).  
- Owns session lifecycle: full reset on `/start` clears in-process state **and** persisted chat history.

### Dialog agent

- **Function-calling agent** (native tool usage).  
- **Per-user memory** persisted in Postgres with token limits and retention policy.  
- **Workflow context** holds booking artifacts (e.g. procedure profiles resolved from search) across turns within a session.  
- **Verified profile** from onboarding injected into every turn — name, phone, registration status — so the model does not re-ask for details.  
- **System prompt** encodes clinic workflow, privacy allow/deny lists, anesthesia pricing rules, and third-party refusal policy.

### Tool layer (nine capabilities)

Each capability is a small, testable unit: async service + thin tool wrapper with JSON schema for the LLM.

| Capability | Role |
|------------|------|
| Procedure search | Natural language → SQL over `medical.procedures`; stores structured profiles for booking |
| Schedule check | Free/busy slots per doctor and date (20-minute grid) |
| Client lookup | Read-only check whether the account owner’s phone exists in the clinic DB |
| Client registration | Starts guided collection of birth date and email; writes client row |
| Current date/time | Grounds relative phrases (“tomorrow”, “next week”) |
| Doctors list | Clinic roster when the client asks who works here |
| Book appointment | Reserves contiguous slots, upserts appointment row, handles mandatory/optional anesthesia pricing |
| List appointments | Upcoming visits for the account owner |
| Cancel appointment | Deletes appointment and frees schedule slots |

Services share one **async Postgres pool**; procedure search uses a **sync SQL path** inside the retriever (LLM-generated SQL executed against the same schema).

### Guardrails (production only)

- Separate **input** and **output** LLM classifiers before/after each agent reply.  
- Block jailbreaks, third-party probing, and leakage of internal fields (IDs, SQL, raw tool JSON) into client-visible text.  
- Disabled in the demo notebook for clarity.

### Data model (PostgreSQL)

- Tables: procedures, doctors, clients, appointments, per-doctor schedule tables, chat memory.  
- **Alembic** migrations for schema evolution.  
- **ETL pipeline** (private) loads doctors, procedures from operational spreadsheets into Postgres.  
- Booking is **slot-aware**: multi-slot procedures mark several 20-minute cells; cancel releases all linked slots.

### Inference

- **vLLM** serves a local open-weight model (OpenAI-compatible API).  
- Agent and guardrails use separate temperature/token profiles; thinking mode configurable per call site.
